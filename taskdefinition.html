Senior DevOps/SRE Technical Assignment

Automated Local Kubernetes Platform

Design and implement a reproducible, Infrastructure-as-Code-managed Kubernetes platform on local virtual machines.

The assessment focuses on outcomes and engineering judgment. Technology choices, architecture, and repository structure are intentionally left to the candidate and must be justified.

Answers in this file are blue. They describe the repository as it stands: Implemented, Partially implemented, Designed but not implemented, Not done, or Out of scope. File paths are relative to the repository root.

1. Scope

Must be implemented

  • Multi-node local virtual infrastructure
    Implemented. vm/Vagrantfile builds 6 libvirt VMs from ansible/inventories/hosts.yaml: 3 control planes and 3 workers.
  • Automated and idempotent Kubernetes provisioning
    Implemented. make k8s up runs ansible/playbooks/k8s-setup.yaml.
  • Production-oriented node and container-runtime tuning
    Implemented. Node tuning, the containerd systemd cgroup driver, the journal cap, kubelet reservations, eviction thresholds, and graceful shutdown are applied to the cluster. Graceful shutdown has not been tested by a real node poweroff.
  • Automatic deployment of a versioned HTTP application
    Implemented. make app up deploys the Helm chart at a vX.Y.Z-release tag. make up runs it.
  • Basic operational visibility
    Partially implemented. make k8s status, kubectl, events, logs, and probes are available. There is no metrics stack.
  • One meaningful failure exercise
    Implemented. make failure pod and make failure node, documented in docs/failure-exercise.md.
  • A single command that validates the implementation
    Implemented. make test runs ansible/playbooks/acceptance-test.yaml.

Must be designed and documented

Implementation is optional for:

  • GitLab CI/CD
    Designed but not implemented as GitLab. The repository uses GitHub Actions (.github/workflows/ci-cd.yml), which is implemented. The design is in docs/ci-cd.md.
  • Production deployment workflow
    Designed but not implemented. docs/ci-cd.md covers the deployment section, and the README covers the deploy path.
  • Rollback workflow
    Designed but not implemented. docs/rollback.md describes the procedure. The helm rollback path has not been run on the cluster.
  • Production monitoring and alerting
    Designed but not implemented. docs/observability.md covers signals, collection, dashboards, alerts, SLOs, access, and failure of the monitoring itself.

Optional bonuses

  • HTTP/application-level autoscaling
    Not done.
  • Monitoring and alerting implementation
    Not done. Designed only, see above.
  • Production-oriented database backend
    Not done. PostgreSQL is a single StatefulSet on a Longhorn volume with no backups and no tested restore.
  • Candidate-developed application
    Not done. The application is the sample app in this repository. The backend has no test files.

2. Platform Requirements

The environment must be recoverable from version control without manually preparing its virtual machines.

The candidate must select and justify the virtualization, configuration-management, Kubernetes bootstrap, container runtime, networking, ingress, storage, and access-control approaches.

The README gives each choice in its topology and local-choices tables. The reasons for each choice are spread across the role READMEs. There is no single decisions document.

The solution must:

  • Use multiple Kubernetes nodes and support replicated workloads.
    Implemented. 3 control planes and 3 workers. The API and web run 2 replicas each, and the ingress runs 2 replicas.
  • Provide functional pod networking, cluster DNS, and ingress.
    Implemented. Cilium 1.20.2 replaces kube-proxy. make test checks cluster DNS, pod-to-pod calls, and ingress on every worker.
  • Provide persistent storage where required by the workload.
    Implemented. Longhorn with 3 replicas. PostgreSQL uses a 5 GiB PVC.
  • Control important software and dependency versions.
    Implemented. Versions and checksums are in ansible/inventories/group_vars/kubernetes.yaml. The app images are tagged by commit and release.
  • Support repeatable creation, destruction, and recreation.
    Implemented. make vm destroy removes the VMs and make up recreates them. A full destroy and recreate was not run in this review.
  • Use modular and maintainable automation.
    Implemented. One role per component, each with a README, and one playbook per workflow.
  • Clearly define ownership when multiple automation systems are used.
    Partially implemented. Ownership is implicit in the code: Vagrant owns the VMs, Ansible owns the host and cluster state and the app Secret, and Helm owns the app release. There is no ownership table yet.
  • Avoid continuous management of the same resource by conflicting systems.
    Partially implemented. Ansible applies the Secret and Helm owns the rest of the chart. The rollout restart that touched the Deployments on every run has been removed, and the v0.1.2 deploy ran without it.

Automation must be idempotent. Repeated execution must not unexpectedly reset the cluster, interrupt healthy workloads, or recreate unchanged resources without justification.

Partially implemented. make k8s up is designed to be idempotent, and the README states it. The app's rollout restart interrupted healthy pods on every run, and it has been removed. The kubelet settings are applied to the cluster. A dry run found that the kubelet config step rewrote the file and restarted every kubelet on each run. That is fixed. A second live run of make k8s up reported changed=0 on all six nodes.

Local simplifications are acceptable, including a non-HA control plane, but they must be identified along with the corresponding production design.

Implemented. The README table "Local simplifications and production design" lists each local choice with its production design. The control plane is HA here (3 nodes), so the non-HA simplification does not apply.

3. Production-Oriented Tuning

Apply and justify operating-system, container-runtime, and Kubernetes-node tuning appropriate to the available resources.

Relevant areas may include:

  • Networking and packet forwarding
    Implemented. net.ipv4.ip_forward and the bridge netfilter settings, in node_tuning/defaults/main.yml.
  • Kernel modules and limits
    Implemented. overlay, br_netfilter, nf_conntrack, and iscsi_tcp are loaded and persisted.
  • File descriptors
    Implemented. DefaultLimitNOFILE=1048576 and fs.file-max=2097152.
  • Connection tracking
    Implemented. nf_conntrack_max=262144.
  • Memory and disk pressure
    Partially implemented. Swap is off and the journal is capped at 500M. The eviction thresholds are applied.
  • Image and log accumulation
    Partially implemented. The journal cap is in place. Image garbage-collection thresholds are not set.
  • Time synchronization
    Implemented. chrony is installed and systemd-timesyncd is disabled.
  • Kubelet resource reservations
    Implemented. systemReserved and kubeReserved are 100m CPU and 256Mi memory each. They are in kubeadm-config.yaml.j2, and kubernetes_base merges them into existing nodes. Each node reports 1800m allocatable CPU.
  • Eviction thresholds
    Implemented. evictionHard is 100Mi memory, 10% node filesystem, 5% inodes, and 15% image filesystem. evictionSoft is 300Mi for 90s.
  • Graceful shutdown and recovery
    Partially implemented. shutdownGracePeriod is 30s, with 10s for critical pods, and is in the kubelet config on every node. A systemd-logind drop-in sets InhibitDelayMaxSec to 60s. The API stops within 10s on SIGTERM. A node shutdown has not been tested.
  • Timezone
    Implemented. node_tuning_timezone is Asia/Tehran, applied to every node. Cloud images default to UTC.

For each important setting, explain:

  1. The problem it addresses
  2. Why the selected value is appropriate
  3. Potential negative effects
  4. How it would be selected or calculated in production
  5. How its application is verified

Implemented for the node tuning settings and the kubelet settings. ansible/roles/node_tuning/README.md has one row per setting with the problem, the value, the downside, the production choice, and the verification step. The kubelet rows are applied, and their allocatable and config checks were run on the cluster.

Generic tuning values copied without reasoning are insufficient.

4. Application

Automatically deploy an immutable, versioned HTTP application as part of the platform bootstrap.

Implemented. Release tags vX.Y.Z-release resolve to a commit. The images are api-<tag> and web-<tag>. make up deploys them.

The application must allow verification of:

  • Liveness
    Partially implemented. The API has a liveness probe on /health. The web container has only a readiness probe.
  • Readiness
    Implemented. Readiness probes on the API (/health) and the web (/). Only ready pods get traffic.
  • Current version
    Partially implemented. The image tag identifies the version. The API does not report its own version, and make test checks the tag.
  • Successful HTTP traffic
    Implemented. make test calls the web and the API through ingress on every worker.

It must also:

  • Run multiple replicas.
    Implemented. The API and web each run 2 replicas. A PodDisruptionBudget with minAvailable: 1 covers each.
  • Define resource requests and limits.
    Implemented in the chart. API: 50m CPU and 64Mi memory requested, 256Mi limit. Web: 10m and 16Mi requested, 64Mi limit. PostgreSQL: 100m and 128Mi requested, 512Mi limit. make test does not check these yet.
  • Run without unnecessary privileges.
    Partially implemented. The API, web, and migrate pods run as non-root with a read-only root filesystem, no privilege escalation, all capabilities dropped, and the RuntimeDefault seccomp profile. PostgreSQL still runs as root. The check is in make test, and it passed on the v0.1.2 deploy.
  • Handle startup and termination gracefully.
    Partially implemented. The API handles SIGTERM with a 10s shutdown. The pod exercise showed a clean stop. The chart sets no terminationGracePeriodSeconds or preStop hook.
  • Route traffic only to healthy instances.
    Implemented. Readiness probes gate the Service endpoints. The pod exercise recorded 0 failed samples with 2 replicas.
  • Remain available during a normal rolling update.
    Partially implemented. Two replicas and a PDB are in place. A rolling update has not been tested on the cluster. The Deployments have no explicit maxSurge or maxUnavailable.
  • Be reachable through the selected ingress approach.
    Implemented. F5 NGINX Ingress on NodePorts 30080 and 30443. Hosts baseapp.local (web) and api.baseapp.local (API).
  • Be traceable to an immutable artifact and source revision.
    Implemented. Each image is tagged with the full commit SHA and the release tag. make app up resolves the tag to its commit and checks it.

Mutable-only tags such as latest are not acceptable.

Implemented. The chart uses only commit and release tags. CI sets latest=false, and make test rejects latest.

Writing the application and exposing application metrics are optional.

Out of scope. The sample app is used. No application metrics are exposed.

5. CI/CD, Deployment, and Rollback Design

A working GitLab pipeline, production deployment workflow, and rollback implementation are not required.

Document a design specific to the submitted platform and detailed enough to implement without making new major architectural decisions.

Designed. docs/ci-cd.md, docs/rollback.md, and docs/observability.md.

CI/CD

Describe:

  • Pipeline triggers and blocking checks
    Implemented. .github/workflows/ci-cd.yml runs on pushes to main, v*-release tags, pull requests, and manual dispatch. The backend go vet and go test, and the web typecheck, must pass before images build.
  • Application, infrastructure, and Kubernetes validation
    Partially implemented. Application checks run in CI, but the backend has no test files. Infrastructure and Kubernetes validation run through make test on the live cluster, not in CI.
  • Secret, dependency, and image scanning
    Partially implemented. make test scans tracked files for secret patterns. Dependency and image scanning are not built.
  • Immutable image publication
    Implemented. Images are tagged with the full commit SHA and the release tag.
  • Release creation and environment promotion
    Partially implemented. Release tags are created by hand. Promotion is done by setting APP_RELEASE. There are no environments.
  • Approval and verification controls
    Designed but not implemented. No GitHub environment or approval gate. Verification is make test, run by hand.
  • Credential protection
    Partially implemented. The Docker Hub token is a GitHub secret, and the images job has contents: read. The deploy uses the controller's admin kubeconfig.
  • Artifact traceability
    Implemented. The commit SHA and the release tag are on every image.
  • Failure handling
    Partially implemented. concurrency cancels superseded runs. There is no retry or notification.

Explain how artifacts would be promoted without rebuilding and how build permissions would be separated from deployment permissions.

Designed but not implemented. docs/ci-cd.md: promote by retagging a digest that main already built, and keep the build identity and the deploy identity separate. Today CI rebuilds the images when a release tag is pushed.

Deployment

Describe:

  • The source of desired state
    Implemented. The Helm chart in app/chart/ plus the values Ansible renders at deploy time.
  • Resource ownership and drift handling
    Partially implemented. Ansible owns the Secret and Helm owns the chart. Drift is not detected.
  • Environment-specific configuration
    Partially implemented. Cluster settings are in group_vars. There is only one environment.
  • Secret delivery
    Implemented. Secrets are generated under ansible/.secrets/app/, which is gitignored. Ansible applies them as a Kubernetes Secret with no_log. The chart reads the Secret by name.
  • Deployment strategy
    Partially implemented. A rolling update through the Deployments. No explicit maxSurge or maxUnavailable.
  • Availability and health verification
    Implemented. helm upgrade --wait --timeout 10m, then rollout status for both Deployments, then make test.
  • Promotion and approval controls
    Designed but not implemented. See the CI/CD section.
  • Failed-deployment behavior
    Partially implemented. --wait makes Helm fail on unhealthy pods. There is no automatic rollback. The migrate Job has backoffLimit: 5.

The same resource must not be continuously managed by conflicting systems.

Partially implemented. No GitOps controller runs, so nothing reconciles the chart in the background. The earlier rollout restart was a second writer on each run, and it has been removed.

Rollback

Describe:

  • How the last healthy release is identified
    Designed but not implemented. docs/rollback.md: Helm history plus the last deploy that passed make test. No deploy log is kept yet.
  • How previous artifacts and configuration remain available
    Implemented. Old tags stay on Docker Hub. Helm history keeps each revision's values.
  • What initiates rollback
    Designed but not implemented. docs/rollback.md lists the triggers: a failed make test, a rise in 5xx after deploy, or a rollout that misses its timeout. The operator decides.
  • Which system performs it
    Designed but not implemented. The preferred path is make app up APP_RELEASE=<previous>. The emergency path is helm rollback, which has not been run.
  • Required permissions and approvals
    Designed but not implemented. Rollback uses the admin kubeconfig today. Production would give it its own role.
  • How recovery is observed and verified
    Designed but not implemented. make test after the rollback, plus the dashboards in docs/observability.md.
  • What happens if rollback fails
    Designed but not implemented. Stop, escalate, and keep the old tags' images, which are never deleted.

Also address incompatible configuration, Kubernetes resource changes, and database migrations where applicable.

Designed but not implemented. Migrations are forward-only, and helm rollback does not run them. The production rule is expand and contract. The emergency rollback is safe only when the schema has not changed.

Rollback must not depend on rebuilding an old artifact, mutable tags, or undocumented manual reconstruction.

Implemented in principle. The old tags exist, and no rebuild is needed. The rollback path has not been tested.
